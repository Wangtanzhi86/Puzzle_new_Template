## 13. 主动建议与风险（需决策）

1. ~~构建管线验证~~ **已完成**：Cocos 3.8.8 的 web-mobile 产物是 **SystemJS + import-map**，
  模块名显式注册，所以内联可行。已用真实产物跑通，在 5MB 内 —— **但余量不宽裕，美术资源总量要卡住**。
2. **图片预算是硬约束**：5MB 减去引擎约 2.5–3MB，真正留给美术的只有 2MB 上下，且 base64 还要涨 33%。
   **美术定稿前先估一版资源体积**，超了再返工成本很高（降分辨率、改用 JPEG、拆关卡都来得及，但重画来不及）。
3. **碎片池顺序**：当前定为"不打乱"（按 `pieceId`）。碎片顺序与缺口一一对应时玩家无需思考，
   试玩时长会偏短。试玩广告通常要在 15–30 秒内制造"想继续玩"的缺口感 —— 可考虑保留 `shuffle` 开关。
4. **吸附半径建议取碎片短边的 20%–30%**：半径过大时手指掠过就吸附，玩家无法"拖着看看"；
   过小则手感发涩。现在是 `PieceSlot.snapRadiusRatio`，默认 0.25，Inspector 里直接调。
5. **对象池 + Layout 的排序坑**：从池中取出的碎片挂回 Layout 时必须 `setParent(content)` 且
   `setSiblingIndex(i)`；回收时不要 `destroy()`，用 `removeFromParent()` 保留实例。
6. ~~横屏布局需要额外的美术决策~~ **已决**：横竖屏共用同一套设计尺寸，重排全交给 Widget + `LandscapeLayout`，
   碎片图不旋转也不压缩。
7. **引擎裁剪放在最后执行**（已写入 §9），裁剪会削弱编辑器调试能力，开发期保留更省事。

# 附录：§16 的「七条踩过的坑」（2026-10-15 从 AGENTS.md 搬来）

> 同上，原样搬来。调参表本身在 [TUNING.md](../TUNING.md)。

七条踩过的坑：

- **揭角按碎片形状逐格配**（2026-10-15，`tools/js/set-slot-peel.js`）：23 格原来抄的是同一份
  （掀右下角 / 比例 0.25），可碎片从 17×34 到 431×140 都有 —— 同一个比例落到长条上是掀掉一大块、
  落到小碎片上几乎看不出来。现在的规则是**按形状算**，全部由脚本现算（不是手调的）：
  1. **掀哪个角**：宽÷高 ≥ 1.2（宽扁的）掀**右边** —— 角取右边缘中点 `(1, 0.5)`，
     折出来的是一条竖折线、整条右边缘翻过去（`peelLine` 的折线本来就不要求过角，任意点都行）；
     其余（竖长的、近正方的）掀**右下角** `(1, 0)`。当前 21 格右下角、`Slot_15`/`Slot_23` 右边。
  2. **掀起多少**：先定折线的**绝对深度** `d = 0.28 × 短边`（世界 px），再折成 `peelLine` 要的比例 ——
     它的 `amount` 是「沿角 → 对角那个方向推多远」，得除以那个方向上的跨度 `span = |ux|·w + |uy|·h`。
     这样无论碎片多大，掀起来那块**占短边的比例都一样**（现在的比例值摊在 0.066–0.228）。
  3. **折线高光带宽**同步按 `d` 折算 —— 它原来写的是「相对碎片高」，落到 775 高的长条上光带就 39px（比折线本身还厚）。
  ⚠️ 它**覆盖**每格手调过的值，换美术 / 碎片尺寸变了要重跑；同一份脚本顺手把 `StickerApply` 那 6 个抄写值
  同步成全局那份（现在没人读，但不一致 `verify-scene.js` 会报一条）。
- **碎片间距早就改成手配的定值了**（2026-10-14）：原来 `PiecePool.fitSpacing` 会在建池子那一下
  **按可视宽度现算**并写回 `content` 的 `spacingX`，那样缝会跟着每一批碎片的宽窄变（两批实测 82.3 / 42.1）。
  现在那套整个删掉了，`spacingX` 就是你在 Inspector 里填的数（场景里 **80**），谁都不覆盖它。
- **整行永远居中**（2026-10-14 起）：那一行的**几何中心**钉在裁剪窗（`view`）的中线上，`spacingX` 填多大都一样 ——
  是 `PiecePool.centerLayoutContent()` 每次排完版**现量子节点占的那一段**量出来的，不是按宽度算的（padding 不对称也照样正）。
  ⚠️ **行宽不等于可视宽**：最宽的一批（451.7 + 两个缝 + 四边 padding）正好卡进 583.893；
  更宽的两头就一起露到框外，**被 `view` 上的 Mask 裁掉，不靠滚动去凑** —— 横轴滚动在 `PiecePool.onLoad` 里
  被关掉了（`ScrollView` 会自己把窄内容左贴边，那是原来「靠左」的根源，力矩见 WORKLOG）。
  四边 padding 与 `spacingX` 一样都在 Inspector 里改；`spacingY` 是横屏竖栏用的，由 `LandscapeLayout` 转屏时现读 `spacingX` 填。
- **亮边的 5 个参数挂在 `PieceFactory` 上，不在 `PieceGlow` 上**：碎片是运行时建的节点，场景里没有实例。
  `GlowConfig` 是个 `@ccclass` 数据类，Inspector 里显示成可折叠分组。
- **收尾那三拍靠「两个数凑一对」排开**（2026-10-15，`tools/js/set-finale.js`）：总修复那道横扫的扫光
  （`RepairSweep`）和完成背景那支画笔（`SceneBgSwap`）**都**挂在「最后一格露面」这一拍上，
  而 §5 不让加事件名、模块间也不许直接拿引用 ⇒ 谁也没法给谁传话，只能各配一个延时：
  `SceneBgSwap.delay = RepairSweep.completeDelay + RepairSweep.completeTime`（现在 0.5 + 0.9 = 1.4）。
  ⚠️ **改任何一个都要重算这一边**：短了是一道光和一杆笔同时上场，长了是白等一截。
  所以 `verify-scene.js` 里有一条专门盯它俩（扫光开关关掉时 `delay` 该填 0，它也报）。
- **「一次飞几批」只能靠让池子一次摆好几屏**（2026-10-15，`AutoPlayer.batches`）：思路本来是「一屏没落完就
  把下一屏也发出去」，但**不行** —— `PiecePool.consumeAll` 是按「池里还剩哪些 entry」补位的，
  半空中的碎片也还在 `_entries` 里，补位那条循环起手 `Tween.stopAllByTarget` 会把它的飞行掐掉
  （`consumeAll` 的注释里写着这条）。于是改成：同一批里所有屏**先一起摆上来**（`PiecePool.buildMore()`，
  接管期间连着叫几次），整批落完再一次性 `consumeAll`。
  ⚠️ 代价是**池子平时一次只摆一屏**（宽度是照裁剪窗 `view` 定的）—— 多摆的那几屏**两头露在框外**，
  所以最外围那两块是**从裁剪窗外面飞进来的**。`batches = 1` 就是老行为。
- **新增 `@property` 后编辑器要刷一次资源库**（MCP `refresh_assets`）才会出现在已有组件实例的 Inspector 上：
  新字段进来了，但场景里那些老实例的属性表还是旧的。**改完 `.ts` 不刷，编辑器内存里跑的还是旧类**。

⚠️ **`tools/js/build-scene.js` 现在是危险动作，别再跑了**：它把 Canvas 下所有层 `removeFromParent` + `destroy`
再重建 —— 换来的不只是上表这些值被复位，而是你手摆的整棵层级一起没了。日常改动走 `tools/js/verify-scene.js`（只读）就够了。
