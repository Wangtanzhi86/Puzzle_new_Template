## 终局跳转：修满 3 个 / 修错 → 跳商店，之后点哪都跳（2026-10-10）

新增 `assets/scripts/platform/EndgameCta.ts`（挂 `Canvas/UILayer/CtaLayer`，接线走
`tools/js/mount-endgame.js`，幂等，scene 上下文，跑完自动存盘）。两条终局：

| 触发 | 表现 | 跳转时机 |
|---|---|---|
| 修满 `winCount`（默认 **3**）个 | **不弹任何界面** | **这一格吸附成功的那一下**（`PIECE_REPAIRED`），不等它的揭晓动画 |
| `REPAIR_FAILED`（`Slot_04` 没达标就被修） | 先把 `CtaRoot/Fail` 整棵淡入（`failFadeTime`，默认 0.25s），再跳 | 等这一格的修复动画演完（`PIECE_SHOWN`）再弹、再跳 |

两条路跳完之后**玩法彻底冻结**：抛出 `GAME_OVER`，然后挂一条全局触摸监听 ——
玩家从商店回来点屏幕任意处就再跳一次（`onTap` 撤掉还没到点的那次 `scheduleOnce` 当场补跳）。

- ⚠️ **修满那条的时机 2026-10-12 改过**（原先是「等这一格的修复动画演完」）：`onRepaired` 里
  不再记 `_endIndex` 等 `PIECE_SHOWN`，改成 `scheduleOnce(finishWin, 0)` —— 吸附那一帧收摊，
  下一帧抛 `GAME_OVER`、再下一帧 `mraid.open`。理由是要「玩家拼上第 4 块就跳走」——
  揭晓动画（贴纸贴平 + 收尾脉冲）那零点几秒不想要了。那一格自己的贴纸动画照旧在后台演
  （没人听 `GAME_OVER`）。
  - ⚠️ **不能同期收摊（踩过，池里会凭空多一块揭着角的碎片）**：`PIECE_REPAIRED` 是
    **在 `PIECE_SNAP_SUCCESS` 派发中途**抛出来的，而 `GameLayer` 上三个组件的顺序是
    `SnapSystem → RepairSystem → DragController`（实测），也就是 **`EndgameCta` 被叫起来的时候
    `DragController` 还没收到那条事件、手上那块碎片还没 `consume`**。同期抛 `GAME_OVER` 的话
    `onGameOver` 会当「拖到一半该冻结了」处理 —— `sendHome` 把那块**送池子里去**（`StickerPeel`
    只认 `PIECE_SNAP_SUCCESS`/`PIECE_SNAP_FAIL` 复位，这里两条都没来，所以还揭着角），
    随后那条 `onSnapSuccess` 因为 `_entry` 已被清空直接 return，碎片就留池里了。
    推到下一帧之后那条派发整段走完（碎片回收、补位、下一屏、`REPAIR_PROGRESS` 与埋点），
    也不再依赖监听顺序。
- **失败路照旧等这一格露面**：`_endIndex` 记下终局那一格的槽位号，只有它的 `PIECE_SHOWN` 对得上
  才动手 —— 理由和扫光 / 完成背景一样，吸附那一 tick 就把事件抛了，画面还要演一两秒，
  而且失败界面得先淡入完（`failFadeTime`）才跳。
- **`REPAIR_FAILED` 是独立终局，不等凑满 `winCount`**，而且它比 `PIECE_REPAIRED` **先抛**
  （`PieceSlot.repair()` 里那句在前面）—— 所以「修满那一块恰好修错」时失败赢：`onFailed` 先把
  `_endIndex` 占了，随后那条 `onRepaired` 的 `_endIndex >= 0` 判空直接跳过。
- `winCount` **填 0 = 不按数量跳**，退回「全部修完 `END_SHOW` → 结束界面」那条老路
  （`CtaController` 那整套代码与场景照旧留着，见上面「结束界面」）。
- `onEnable` / `onDisable` 严格对称：三条 `EventBus` + `failButton` 的 `CLICK` + 全局 `input`。
  `Fail/btn` 自己也绑了 `CLICK` 跳商店（它认领自己那块矩形，落上去的触摸到不了全局那条）；
  `Fail/bg` 虽然铺满全屏但**没挂任何监听**，落在它上面的点击照样进全局。

## 自动打关：玩家修够几块之后系统接管（2026-10-15）

**要的是什么**：给投放版本一条「保底走到 CTA」的保险 —— 玩家自己修够 `AutoPlayer.afterPlaced` 块之后，
系统收掉玩家输入，把剩下的碎片放完。总开关是 `Canvas` 上 `FeatureFlags` 面板的
「自动打关」，**默认关**（`DEFAULTS.autoPlay = false`，它是唯一不在 `DEFAULTS` 里全开的开关：
它改的是玩法本身，面板丢了该退回「玩家自己修完」，而不是替他打完）。

**节奏是「一批一批」的**：每一步把池里**此刻摆出来的 `batches` 屏**（一屏 = `PiecePool.batchSize` 块，
默认一次摆 2 屏）一起放走，整批落地后才消耗、池子才补下一批，隔 `gap` 秒放下一批。
一批之内块与块之间错开 `stagger` 起飞 —— 因为整批完全同时飞看着太机械，
像一群东西被一根杆子推出去；错开一点就有了先后和错落感。
所以一批的用时 = `(块数-1) × stagger + flyTime`；`gap` 是批与批之间的停顿，
**不是**块与块之间的间隔。想一块一块看就把 `batchSize` 调成 1；想回到「一屏一屏放」把 `batches` 填 1。

- 2026-10-15 从「一块接一块」改成「**一屏一屏**」：一屏 = `batchSize` 块，同屏内错开 `stagger`。
- 2026-10-15 又改成「**一次飞两批**」（`batches = 2`）：一屏一屏放的话，玩家先手 3 块之后还剩 20 块，
  要 7 轮，每轮都得「起飞一轮 → 落地 → 补屏 → 歇 `gap`」走一遍，整段比修图本身还长。
  两批一起摆在台上的复用率更高：同样的碎片数变成 4 轮（6 / 6 / 6 / 2），省掉的是**每轮那份固定开销**
  （一次补屏 + 一次 `gap` + 一次起飞）。⚠️ 省下的绝对值跟着 `gap` / `flyTime` 走 ——
  现在场景里调得很紧（`stagger 0.01` / `gap 0.02` / `flyTime 0.1`），所以只省 1/3 左右；
  调回 `flyTime 0.4` / `gap 0.3` 那种松节奏时，省的是 2 秒上下。

⚠️ **「一次飞两批」不是「一屏没落完就把下一屏也发出去」**——那样做不了：`consumeAll` 是按
「池里还剩哪些 entry」补位的，而半空中的碎片也还在 `_entries` 里，补位那条循环起手
`Tween.stopAllByTarget` 会把兄弟的飞行 tween 掐掉（就是下面「一批必须一次消耗完」那个坑）。
所以是**先把两屏都摆上台**（`PiecePool.buildMore()`，接管期间连着叫几次），**整批一起消耗**。
代价：池子平时一次只摆一屏（宽度是照裁剪窗 `view` 定的），多摆的那一屏**两头露在框外**，
所以**最外围那两块是从裁剪窗外面飞进来的** —— 观感可接受（它们本来就是「从池子里飞出来」），
但别把 `batches` 调到 3 以上，那会一次摆出去 9 块、露在框外的比例明显变大。

⚠️ **顺带补掉一个换批淡入的坑**：`buildBatch` 的淡入是给 `UIOpacity` 起一条 0.5s 的 tween，
而对象池把节点**原样**还回来（`recycle` 只 `_pool.put`）。一次一屏时没人撞得上 —— 一屏放完到补下一屏
本来就过了一个 `gap`，早超过 `batchFadeTime` 了。一次飞两批之后节奏压得很紧（`flyTime 0.1` + `gap 0.02`），
**新一批拿到的正是刚还回去的那几个节点**，而它们身上那条淡入还没跑完 —— 两条 tween 一起写 opacity，
新的一块会直接亮着出现（淡入那条被压掉了）。修法是在置 0 之前先 `Tween.stopAllByTarget(op)`。
加了这一句之后 `batchFadeTime` 填多长都不会出问题（被掐掉的都是已经修好、看不见的那一块身上的 tween）。

⚠️ **错峰排在 `launch` 调用处（`scheduleOnce`），不是 tween 的 `.delay()`**：`.delay()` 只推后飞行，
`takeOut` / `PIECE_PICK`（揭角那一套）还是同一刻全发生 —— 先飞的那块会举着已经掀开的角在原地等自己那块的表，
错落感是假的。排在 `launch` 外面则是「这一块整条动作都晚一点开始」，池子看起来是一块接一块被拿走的。

**怎么接的**：新组件 [assets/scripts/gameplay/AutoPlayer.ts](../../assets/scripts/gameplay/AutoPlayer.ts)，
挂 `Canvas/GameLayer`（和 `DragController` 同节点），接线走 `tools/js/mount-auto-play.js`。
它每一块走的路和玩家**完全一样**，一步都没绕：

```
takeOut（原位留 Spacer）→ 抛 PIECE_PICK（揭角 / 光边 / 拖尾照旧跟着这块碎片）
  → tween worldPosition + scale（按 carryHeight 放大到缺口大小）—— 整批按 stagger 错峰起跑
  → 落点抛 PIECE_DRAG（位置就是 worldCenter，吸附判定照旧交给 SnapSystem）
  → 抛 PIECE_SNAP_SUCCESS → RepairSystem.repair → 揭晓 / 进度 / 音阶 / 埋点
  → 整批都落地之后 consumeAll（和 DragController.onSnapSuccess 同一个次序：排在抛事件后面）
  → scheduleOnce(step, gap)
```

所以揭晓、音阶、进度条、埋点、`winCount` 到点跳商店**一行都没改**，全部照常发生。

**为什么新加一个 `AUTO_PLAY` 事件，而不是复用 `GAME_OVER`**：`GAME_OVER` 看着正合适
（`DragController` 收到就摘掉 `content` 的触摸监听、`PiecePool` 锁滚动、`GuideController` 收引导 ——
三件都是想要的），但 `PlayableAnalytics` 把它当 `CHALLENGE_SOLVED` 上报。
接管那一刻整张图远没修完，报了就是假数据。所以另起一个名字，只做「收手」这一件事。

⚠️ **接管之后贴纸那一下收尾脉冲不演**（一屏 3 块同时落地、每块各缩各淡会糊成一片闪）：
`StickerApply` 挂一个 `AUTO_PLAY` 监听，`settle()` 里判断一下就跳过 —— 发射方没动，见
「三件表现调整」那一节。

**三个踩过的边**：

- **一批必须一次消耗完 —— 这是「整屏」这一版真正的坑**。原来的 `consume(entry)` 一次只收一块，
  而补位那段循环起手就对**每个还在 `_entries` 里的碎片** `Tween.stopAllByTarget(node)`；
  半空中的碎片也在 `_entries` 里（`takeOut` 只换节点父级，entry 不摘）。所以「每落地一块就
  `consume` 一次」会把**同一屏里还在飞的兄弟**的飞行 tween 掐掉 —— 它们永远落不了地，
  `_pending` 归不了零，链条当场卡死（画面停在几块碎片悬在半空）。
  修法是把批量消耗做成一个动作：`PiecePool.consumeAll(entries)`，
  `consume(entry)` 改成 `consumeAll([entry])`。一起调还顺带只排一次版、只滑一次位，
  **整屏的补位是同时起跑的**，比逐个收好看。函数上的 ⚠️ 注释就是这条。
- **`GAME_OVER` 要把还在排队的接管撤掉**。`afterPlaced` 配到 `winCount` 以上时（比如两个都填 6），
  玩家自己就修满了，下一帧 `EndgameCta` 就跳商店 —— 而接管还排在 `startDelay` 里没起飞，
  不撤的话它会在商店已经开着的时候往空池子里抓碎片。`AutoPlayer.onGameOver` 就是这三行。
- **`takeOut` 会换父节点**（`content` → `dragRoot`），而 Cocos 的 `setParent` 默认保的是**局部**坐标 ——
  起飞前必须先把世界位置记下来、再 `setWorldPosition` 放回去。`DragController.onStart` 是紧接着
  覆盖成手指位置，所以看不出这一步，照抄会漏（碎片会先跳一下）。

⚠️ **还没验的部分**：只在编辑器里核了接线与开关值（`verify-scene.js` 报 `AutoPlayer @ GameLayer`），
**Game View 里没跑过**。要看的是：接管那一刻玩家手上那块（如果正拿着）被立刻放回池子、
随后作为第一批的一块飞出去；一批几块是不是真的按 `stagger` 错落起飞、落点整齐；
**一次摆两屏时最外围那两块从裁剪窗外飞进来**这一下是不是扎眼（扎眼就把 `batches` 填回 1）；
`gap` / `flyTime` 调大调小的观感；以及最后一批落地到跳商店那段是否和玩家自己修完一样。
