# 打包期图片重压：PNG/JPG/WebP 统一转有损 WebP，产物 5.60MB → 4.04MB

- 日期：2026-10-21
- 提交：<提交后回填>
- 关联：AGENTS.md §8.5 / §9

## 改了什么

- `tools/lib/assets.mjs` 的 `toWebp()` 扩成 `toWebp(files, { uiQuality, photoQuality })`：
  - `.png`：无损（method 6/4）+ 有损（uiQuality、photoQuality）四个候选，取最小；
  - `.jpg`：只试有损 photoQuality，压不过原图就保留原 JPG；
  - `.webp`：已有 WebP 也重压一遍（序列帧原图是高质量导出，收益最大）。
  - UI 与照片/序列帧分开质量，新增 `@jsquash/jpeg` 依赖（jpg 解码用）。
- `tools/pack-playable.mjs` 新增 `--tag <名字>`（产物另存到 `build/<名字>/`，不覆盖默认三份）、
  `--ui-quality` / `--photo-quality`；本项目当时定档 **94 / 92**（其余参数仍为默认）。
  > 2026-10-22 因新素材让产物涨到 5.15MB，默认已降到 **90 / 86**，见
  > [2026-10-22-构建体积回落到5MB内.md](2026-10-22-构建体积回落到5MB内.md)。

## 为什么这么改

- 超限的 5.60MB 里 4.16MB（gzip 后）是 native 美术，引擎只占 0.43MB —— 继续裁引擎收益很小。
- 原打包器只把 PNG 转**无损** WebP；实测这批图（UI、序列帧）用有损 WebP 质量 88/80 即可省
  1.6MB，视觉上分辨不出。序列帧 17 张 480×854 从 1.14MB 降到约 0.41MB，是最大头。
- 否掉的方案：JPG→WebP。实测 928×1152 的选关封面 q82 反而比原 JPG 大（120KB vs 91KB），
  原 JPG 已经压得很狠，强转只会变大 —— 所以逻辑是「压不过就留原图」。
- 扩展名不改（仍是 .png/.jpg）：运行时按魔数识图、不给图片 MIME，这一条 8.5 节原本就依赖。

## 怎么验的

- `node tools/pack-playable.mjs --report --ui-quality 88 --photo-quality 80` → 3.99MB。
- 三档实打包 + 自检全过（载荷 base85 往返校验、CTA 明文、无外链）：
  - `build/q94`  ui94/photo92 → 4.46MB
  - `build/q92`  ui92/photo88 → 4.25MB
  - `build/q88`  ui88/photo80 → 3.99MB
- 定档后按默认（ui94/photo92）重打根目录三份 → **4.46MB**，余量 0.54MB，自检全过。

## 影响什么 / 还没验的部分

- 只改打包期字节，构建目录、美术源文件、Cocos 工程都不动；编辑器里正常构建后自动走新逻辑。
- 有损压缩的观感需要人眼确认（本次没有截图比对）：建议三档都开一遍，看 UI 文字边缘、角色序列帧。
- 真机（iOS WKWebView / Android WebView）尚未验证，尤其大图 WebP 解码耗时。
